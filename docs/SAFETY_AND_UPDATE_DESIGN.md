## 0. 设计原则

1. **复位不是安全动作。** MCU 复位会让 PWM 失去控制。看门狗是**卡死检测器**，不是安全停机器。真正的安全动作永远在软件里、在复位之前完成。
2. **每一处判断只由一个位置负责。** 不设通用错误标志决定全部停机行为；不设两套并存的停机条件。
3. **职责按"只有谁能做"划分，不按"谁方便"划分。** 传输完整性归 S3/PC（只有它是接收方）；记录完整性归 STM32 Bootloader（只有它知道自己在写记录时可能断过电）。
4. **不做不可逆的事。** 不提升防回滚计数，不使用会使旧版本无法启动的机制。
5. **分两期实施。** 一期不依赖协议扩展，可全部主机验证；二期依赖 RFS1 扩展。
6. **启动限制与运行中降级分开判断。** 不能用"一个错误标志"决定全部停机行为。

## 2. STM32 Flash 布局

F405，1 MiB 单 Bank，**扇区不等大**。

### 2.1 扇区几何（RM0090）

| 扇区 | 起始 | 大小 | 扇区 | 起始 | 大小 |
|---|---|---|---|---|---|
| 0 | `0x08000000` | 16 KiB | 4 | `0x08010000` | 64 KiB |
| 1 | `0x08004000` | 16 KiB | 5 | `0x08020000` | 128 KiB |
| 2 | `0x08008000` | 16 KiB | 6 | `0x08040000` | 128 KiB |
| 3 | `0x0800C000` | 16 KiB | 7 | `0x08060000` | 128 KiB |
| | | | 8–11 | `0x08080000` … `0x08100000` | 4 × 128 KiB |

扇区 0–3 是**四个独立的 16 KiB 扇区**，无法把一个 64 KiB 块切成 `32 + 16 + 16` 之外的形状。

### 2.2 布局

| 区域 | 扇区 | 地址区间 | 容量 | 链接约束 |
|---|---|---|---|---|
| Bootloader | 0–1 | `[0x08000000, 0x08008000)` | 32 KiB | `LENGTH = 32K` + ASSERT |
| 启动记录 0 | 2 | `[0x08008000, 0x0800C000)` | 16 KiB | 不参与链接 |
| 启动记录 1 | 3 | `[0x0800C000, 0x08010000)` | 16 KiB | 不参与链接 |
| APP A | 4–7 | `[0x08010000, 0x08080000)` | 448 KiB | `ORIGIN = 0x08010000` `LENGTH = 448K` |
| APP B | 8–11 | `[0x08080000, 0x08100000)` | **448 KiB 可用**（物理 512 KiB） | `ORIGIN = 0x08080000` `LENGTH = 448K` |

- **两份记录位于扇区 2 与扇区 3，是两个独立扇区**，满足"记录必须位于不同物理擦除扇区"。更新任一份记录只擦它自己那一个扇区。
- **可发布应用上限是单一常量 448 KiB，两槽共用。** APP B 白送的 64 KiB 不分配给任何人，避免出现"只能烧 B 槽"的镜像。
- F405 使用**软件选择应用的 A/B**，不依赖其他 STM32 型号的硬件双 Bank 切换。
- 实测尺寸（供参考，非上限）：
  - 本轮Release BIN：59124B（含装载间隙，以BIN/manifest为准）。
  - 本轮Debug BIN：99748B。
  - 本轮Bootloader BIN：2208B；32KiB由链接器与CTest约束。

### 2.3 链接脚本约束（必须做，否则静默覆盖）

当前 `STM32F405RGTx_FLASH.ld` 使用 `ORIGIN = 0x08000000, LENGTH = 1024K`。**应用若沿用此脚本会从 `0x08000000` 铺开，必然覆盖 Bootloader 和两份记录，且编译不报错。**

三套链接配置，各自带链接期断言：

```
; Bootloader
FLASH : ORIGIN = 0x08000000, LENGTH = 32K
ASSERT(LOADADDR(.data) + SIZEOF(.data) <= 0x08008000, "Bootloader exceeds 32KiB")

; APP A
FLASH : ORIGIN = 0x08010000, LENGTH = 448K
ASSERT(LOADADDR(.data) + SIZEOF(.data) <= 0x08080000, "APP A exceeds 448KiB")

; APP B
FLASH : ORIGIN = 0x08080000, LENGTH = 448K
ASSERT(LOADADDR(.data) + SIZEOF(.data) <= 0x080F0000, "APP B exceeds 448KiB")
```

- Bootloader 编译固定使用 `-Os` + `-ffunction-sections -fdata-sections` + `-Wl,--gc-sections`。
- CTest 中增加一条 Bootloader 尺寸检查（复用现有 `verify_stm32_target.py` 的 ELF 读取框架）。
- **给 Bootloader 增加调试日志前先量尺寸**，防止 Debug 级膨胀越过 32 KiB。
- 同一份源码分别链接生成 A/B 固件：**普通 GCC 应用的绝对地址不能靠修改 VTOR 自动重定位**，必须分别链接。

### 2.4 向量表与 RAM 约束

- Bootloader 向量表固定 `0x08000000`；APP A 固定 `0x08010000`；APP B 固定 `0x08080000`；槽起点 **512 字节对齐**。
- 应用 `SystemInit` 必须写入对应槽的 `SCB->VTOR`，**不得跳转后又改回零偏移**。
- 初始 MSP 检查：**8 字节对齐**且 `0x20000000 < MSP <= 0x20020000`（允许等于 RAM 末端）。
- 初始MSP为0x2001FFC0；合法范围为0x20000000 < MSP <= 0x2001FFC0且8字节对齐。普通RAM占用20408B，另有64B固定故障记录；布局和栈顶由三种ELF检查。
- `.noinit.fault`固定在0x2001FFC0的64字节独立NOLOAD区域，Bootloader/A/B链接器均排除此区域并降低栈顶；魔术字、版本、CRC和最后提交标记校验。POR/BOR后不信任旧内容，启动读取后消费一次。

### 2.5 链接脚本、Bootloader、打包器、升级器必须共用一套布局定义

- 链接脚本、Bootloader、打包器、S3 升级器、OpenOCD 脚本使用**同一套固定布局定义**，不能各自维护不同地址。
- STM32 侧与 S3 侧使用**不同的**镜像头校验：S3 用 ESP-IDF 镜像头 + 芯片/版本/段范围 + OTA 分区校验，**不套用 ARM 的 MSP/VTOR 检查**。

## 3. 启动记录

### 3.1 字段（建议）

| 字段 | 说明 |
|---|---|
| 代次 sequence | 递增；用于在两份记录中选较新者 |
| 目标槽 | A / B |
| 镜像长度 | 写入时记录，与清单一致 |
| 镜像摘要 | **S3 在写入前算好的 CRC32 期望值**（§4.2 约定） |
| 已确认槽 | 当前可信槽（回滚目标） |
| 待试运行状态 | 该槽是否处于试运行 |
| 试运行已用次数 | 有上限，防止反复试同一个坏镜像 |
| 记录 CRC32 | 覆盖记录内容 |

只有**完整有效**的记录参与槽选择。

### 3.2 写入协议：最后写标记位（防半写）

```
1. 擦除目标记录扇区
2. 写入完整记录内容 + CRC，最后一个32位提交字保持0xFFFFFFFF（不参与CRC）
3. 读回，确认内容与 CRC 均正确
4. 单独写入提交字0xA55AA55A
```

- 提交字必须精确匹配且记录CRC、字段范围均正确；提交中断电可能留下部分位已写的值，并非保证仍为全FF。它不满足完整提交条件，不参与选择。
- **不同时擦两份记录。** 需要切换记录扇区时，先在另一扇区建立并读回有效新记录，再回收旧扇区。
- **试运行的"开始"状态必须先在另一扇区落盘、读回有效，再跳转**，确保未确认复位不会反复试同一个坏镜像。

### 3.3 两份记录均不可用时

留在安全 Bootloader，由 S3 的持久恢复包经受限 SWD 恢复。**不猜测执行半写镜像。**

## 4. 校验职责划分

| 校验对象 | 责任方 | 时机 | 开销 |
|---|---|---|---|
| 镜像 SHA-256（传输完整性） | S3 / PC | 上传后、写入前 | S3 算力 |
| 镜像 CRC32 期望值 | S3 / PC | 上传后、写入前，写入清单与记录 | S3 算力 |
| **整镜像 CRC32（写入完整性）** | **STM32 Bootloader** | **每次启动** | F405硬件CRC，整体时间待实测 |
| **记录自身 CRC32** | **STM32 Bootloader** | 每次启动 | 微秒级 |
| **向量表 / MSP / PC 合法性** | **STM32 Bootloader** | 每次启动 | 微秒级 |

### 4.1 Bootloader 必须对整镜像做完整性检查

**不能只用向量表 / 前 1 KiB / 镜像头代替整镜像校验。** 原因：镜像头先写完、尾部尚未写完时，**向量表和头部完全可能合法**，只查头部会把半写镜像当成完整镜像跳转。

正确的防半写机制是**两层**，两层都必须有：

1. **记录状态机（防"跳到不该跳的槽"）** —— 完整镜像读回验证通过后才提交待试运行记录；提交前旧选择始终有效；最后写标记位防止记录自身半写。写镜像过程中断电时记录仍指向旧槽，所以 Bootloader 不会被引向半写槽。
2. **Bootloader 整镜像 CRC（防"记录指向的槽已经坏了"）** —— 覆盖第 1 层管不到的情况：记录提交后镜像区段被破坏、CRC 覆盖不到的部位被改、或记录与镜像不一致。**这是唯一能独立确认"我要跳的这段代码是完整的"的手段。**

### 4.2 CRC 算法与预期值来源

- **F405 有独立硬件 CRC 外设**（RM0090 CRC 章节），可用并优先使用，不要用软件逐位实现。
- F405每32位字需4个HCLK。448KiB纯CRC计算在168MHz约2.73ms、16MHz约28.67ms，不含CPU搬运和循环开销；Bootloader当前沿用复位HSI时钟，不能套用应用168MHz。整体时间必须实测。
- **多项式、初始值、输入/输出反射与末尾异或必须在两端显式约定并写成常量。** 硬件 CRC 的默认行为与 PC 上 `zlib` 的 `crc32()` **不等价**（后者带末尾异或等约定），直接比较会永远不一致。S3 在流式接收镜像时同步计算并存入清单与启动记录，Bootloader 用硬件 CRC 重算比对。
- 若实测结果超预算，**先优化启动宽限（§4.3），不得以"启动要快"为由删除整镜像校验。**

### 4.3 启动通信宽限

校验耗时与 S3 侧 `RF_SPI_OFFLINE_MS = 100 ms` 的冲突，**由通信宽限解决，不由删掉完整性检查解决**：

- **S3 侧**：在 STM32 复位后的启动宽限窗口内（宽限值 = 最大启动校验时间 + 余量，具名常量），**不**报告"STM32 通信中断"，**不**把 SPI 断链列为禁止启动原因。
- **STM32 侧**：Bootloader 完成校验并跳转后，应用在第一次可应答前不改变链路语义。
- 本项需要 S3 侧配合改动，是本文少数**跨端约束**之一；**不扩 RFS1 字段**，只改 S3 的离线判定窗口。
- 宽限窗口内**不得放行运动启动**（与 §5.3 规则 1 的"SPI 断链"处理一致）。

## 5. 应用状态机与裁决顺序

### 5.1 状态

`WAIT_COMMAND` 等待 · `RUNNING` 运行 · `SURFACE` 浮力上浮 · `BATTERY_STOP` 电池停机

- 控制来源（LoRa / 2.4G / 无）**单独记录**，不作为状态。
- 升级锁是 `WAIT_COMMAND` 的**禁止启动原因**，不新增状态。
- **普通告警不新增状态。**
- 状态用 Latest Value，指令/退出用有界事件；不建设通用消息框架，不新增喂狗任务。

### 5.2 裁决顺序（自上而下，先命中者胜）

1. **致命执行故障** → 故障出口路径（§8.5），不要求卡死任务还能推进状态机。
2. **电池异常**（低压 / 过压 / 无效 / 样本过期）→ `BATTERY_STOP`，覆盖人工控制与上浮。
3. **全停 / 退出 / 升级锁** → 撤销运动授权。**辅助设置与心跳不能解除**。
4. **`WAIT_COMMAND`** → 只检查启动条件并接收新的有效运动指令；**不因链路缺失自动上浮**。
5. **`RUNNING`** → 选 LoRa（一期唯一来源）；目标失效 → `SURFACE`。

### 5.3 业务规则表

| # | 阶段 / 情形 | 动作 | 期次 |
|---|---|---|---|
| 1 | 开机、全停或复位后，S3 正在烧录 / SPI 断链 / 控制来源不可用 | 禁止开始运动；网页列出全部当前禁止启动原因；条件解除后仍需**新的有效运动指令** | 一期（SPI）/ 二期（S3 烧录） |
| 2 | 运行中，有有效 LoRa 控制 | 优先 LoRa；S3/SPI 断链只记诊断，**不打断健康 LoRa** | 一期 |
| 3 | 运行中，LoRa 失联，有新的有效 2.4G 目标 | 使用 2.4G；**不执行失联前缓存的旧网页目标** | 二期 |
| 4 | 运行中，所有控制来源不可用 | → `SURFACE`：双桨停转，四舵机保持最后成功写入角度 | 一期（= LoRa 失联） |
| 5 | 上浮或 2.4G 期间收到新的有效 LoRa 运动指令 | LoRa 优先接回；**仅恢复链路，不恢复旧目标** | 一期 |
| 6 | 收到 STOP 17 或退出控制 | 保持停机；随后失联**不**自动启动、**不**自动上浮；等待新的有效运动指令 | 一期 |
| 7 | 看门狗复位 | 清除旧目标，保持停机；满足启动条件后等待新的有效指令 | 一期 |
| 8 | 电池低压 / 过压 / 无效 / 样本过期 | 执行电池停机，覆盖人工控制与上浮；电压恢复后仍须新的有效运动指令 | ✅ 已完成 |
| 9 | 一般告警 | 网页显示原因，**不因告警本身停止鱼** | 一期 |
| 10 | 执行 S3 或 STM32 升级 | 必须先全停；升级期间拒绝启动。运行中可上传并缓存文件；**应用区擦写、启动项切换、重启均在全停后执行** | 二期（锁）/ 一期（流程） |

电池参数沿用现状：**6.6–8.4 V（含边界）**，样本最大年龄 **500 ms**，**先检查未滤波电压**。未重新标定硬件阈值。

"有 LoRa / 2.4G"指**有可用的控制来源及有效的新鲜目标**，不能用"串口有字节""AP 有人连接""SPI 心跳正常"替代。**具体有效期仍待确定**（§16）。

### 5.4 链路与指令有效期：三件不同的事

**接收任务活着、链路有新帧、运动目标仍获操作者续期，是三件不同的事。**

- `observeLoRa()` 的周期调用**不能**替代操作者控制会话；
- SPI 心跳**不能**替代操作者控制会话；
- **不能拿 S3 本地 SPI 心跳替代 2.4G 的目标续期。**

由此得出：

- **LoRa 发送端需要约定周期保活 / 目标续期。** 只给"当前偶发命令"增加超时，会把**保持动作期间不发包**误判为失联。
- **2.4G 也需要网页会话 / 目标续期**；备用接管**只接受失联后的新的有效目标**。
- **LoRa、网页、任务期限、IWDG 时间分开配置**，比较均支持回绕。
- **现有 SPI 离线诊断阈值 100 ms 保留，不冒充 LoRa 超时。**
- 当前"来源号 + 序号"**还不能独自识别 STM32 复位前遗留的帧**；实施前须确定启动解锁 / 新会话规则，**不擅自增加时间戳**（§16）。
- **LoRa 发送端本轮仍未修改。**

### 5.5 STOP 编号语义

- **STOP 1**：保留原有水平停止语义。**不等同** STOP 17 或退出。
- **STOP 17**：全停。进入停机屏障（§7）。
- 任何退出 / 电池保护 / 复位后的旧队列、旧回调、旧视觉结果**都不能重新授权运动**。
- **旧包、重复运动事件不能无限延长旧目标。** 重发同一事件必须保持来源号、序号与载荷，**不能通过不断递增序号重放模式循环等切换事件**。
- **STOP 送达还需发送端确认/重发配合**，这是发送端责任（本轮未修改发送端）。

## 6. 浮力上浮（SURFACE）与退出

用户选择：**双桨停转、舵机不动。**

### 6.1 进入时

1. 冻结四个舵机的**当前设定角度**（驱动接受的值，**不是位置反馈**）；
2. 撤销旧来源授权；
3. 清除：水平 / 转向目标、摆尾、PID 积分、自动目标、未完成过渡、pending 事件；
4. 推进控制代次（generation），使所有在途异步结果失效。

### 6.2 每周期提交

- 四个舵机：冻结角度（继续输出该角度的 PWM，**不主动设置新的姿态**）；
- 两路 ESC：**立即中立，跳过油门缓动，不做反向刹车**；
- 关闭造流辅助；
- 前馈必须保证**零输入仍为零**。

**不得复用 LoRa 代码 6**：它会保留旧水平目标并允许造流。

### 6.3 维持与退出

- 维持至新的有效人工运动指令接管，或被全停 / 电池停机覆盖；
- 实际回浮依靠自身浮力；**固件不检测是否到水面**；
- **不清除 LoRa 序号防重水位**；
- **不等待通信 ACK 才停机。**

## 7. 退出屏障

统一退出清理（全停 / 电池停机 / 复位 / 升级锁 **共用同一条路径**）：

1. 推进控制代次 → 旧队列、旧回调、旧视觉结果全部失效；
2. 取消旧目标 / 事件 / PID / 过渡 / pending；
3. 释放所属异步事务资源；
4. 记录原因及**实际写入通道掩码**；
5. 提交输出：
   - 主动全停与电池停机：**立即提交全部中立**；
   - 浮力上浮：保留冻结的舵机角度。

**六路 PWM 非原子更新**，部分写入**不能**报告全部成功（沿用现有 `writtenMask` 语义）。

**视觉 / PID / 自动化保留，但不得绕过人工控制优先级、电池保护与退出屏障。**

## 8. 看门狗与致命故障出口

### 8.1 核心原则

> **看门狗处理关键任务未在各自期限内完成工作；业务状态和一般输出告警不直接取消喂狗。**
> **"任务在运行但做不成事"由应用自己有限重试 + 受控复位处理，且全程继续喂狗。**

理由见 §0 原则 1：复位会让 PWM 失去控制。若电调保持最后的有效 PWM 值（待实测，见 §14 第 1 项），**带着全速螺旋桨复位比不复位更危险**。

### 8.2 归属与启动时机

**必须覆盖"应用启动阶段卡死"。** 新固件若卡在电调等待、驱动初始化或任务创建阶段，没有看门狗就永远不会复位，也就**永远不会触发回滚** —— 这是与升级可靠性直接相关的一条，不是纯运行时问题。

因此：

- **Bootloader 全程不启用 IWDG**（避免 2 秒启动路径被不对的超时打断，也避免交接窗口）。
- 应用Reset_Handler首个函数调用启用IWDG，早于SystemInit、数据/BSS初始化和C++构造；不依赖HAL时基、不等待RTOS。
- **初始化完成后重设为运行预算。** IWDG 的"不可软件关闭"指的是**不能停用**，不是不能改超时：通过写 `IWDG_PR` / `IWDG_RLR` 并等 `IWDG_SR` 的 PVU/RVU 清零可以重设周期（F4 需按 RM0090 要求处理更新等待，且改动期间可能提前超时，**必须实测**）。
- 启动预算覆盖原有2000ms vTaskDelay等待，不增加后台周期喂狗；等待已让出CPU。首次喂狗须RadioPoll/Control完成实际工作，试运行还须连续3轮中立写入成功并持久确认。
- 本轮使用两阶段预算：启动PR=4/RLR=4095，运行PR=4/RLR=255；运行期非阻塞检查SR更新完成才重载。名义LSI=32kHz，公差与重设行为上板测量。
- 早期IWDG负责真正产生复位；Bootloader在跳转前持久写TRYING及已用次数，最多试运行一次，未确认复位即回旧槽。次数上限本身不会产生复位。
- 代价：Bootloader 自身无看门狗保护，依靠选项字节写保护 + 有线恢复兜底。这与"USB/SWD 整片覆盖不属于受保护 OTA 范围"一致。
- **Idle、SysTick、定时器、DMA 中断不喂狗。**
- **调试暂停冻结看门狗不等于执行器已停。**

### 8.3 喂狗条件：按各任务自己的期限

```
喂狗 ⟺ 每个"在册"任务都满足 (now − 该任务最后完成时间) < 该任务自己的期限
```

**不能要求每个控制周期内所有任务计数都变化。** 那个条件是错的，理由：

- 各任务周期本来就不同（RadioPoll 10 ms、MotionControl 20 ms、Vision 20 ms）；
- 合法的调度错位会让某个任务在一个控制周期内恰好没完成一轮；
- 较慢的任务（例如带 Flash 访问或 UART 的空闲任务）本来就跨多个周期。

误判的后果是**看门狗复位一条完全健康的鱼**。

实现要点：

- 每个任务维护 `std::atomic<uint32_t> lastDoneTick[idx]`，在**主循环末尾**写入自己的完成时间（"跑完一轮"才写）；
- 每个任务有**独立的具名期限常量**（例如任务周期的 3–5 倍），期限与 IWDG 周期**分开配置**；
- `MotionController` 喂狗前逐任务比较 `now − lastDoneTick[idx] < deadline[idx]`，任一超期 → **不喂**；
- **跨任务同步用 `std::atomic<uint32_t>`，不用 `volatile`。** `volatile` 只阻止编译器优化读写，**不提供跨任务的可见性与顺序保证**，不能承担同步职责；
- 未启用的视觉任务**不**在册（不要求其数据进度）；
- **不得**用"任务句柄存在"或"tick 计数在涨"替代完成时间；
- 所有时间比较**支持回绕**（用 `static_cast<int32_t>(now - last)` 形式，与现有 `rf_spi_after` / `due()` 一致）。

> **关键限定：喂狗与业务状态无关。** `SURFACE`、`WAIT_COMMAND`、`BATTERY_STOP`、无线无数据时**一律继续喂狗**。只要任务仍被正常调度且在各自期限内完成，就必须喂。这些状态是正常运行，不是故障。
>
> **最容易犯的错误：把"喂狗"和"有运动"绑在一起 → 浮力上浮会被自己的看门狗打断。**

### 8.4 输出失败：升级阶梯（不停喂狗）

| 累计连续失败 | 动作 | 喂狗 |
|---|---|---|
| 1 | 记一般告警，下一周期继续提交 | ✅ 继续 |
| 2 … N−1（N = 5，约 100 ms） | 记告警，继续重试 | ✅ 继续 |
| ≥ N | 进入"执行故障"上报状态，**持续重试写中立值** | ✅ 继续 |
| ≥ M（联调初值15） | 禁普通输出 → 专用中立及记录 → 保留40ms窗口 → 主动复位 | 窗口内健康任务继续 |

- `consecutiveWriteFailures` 是**单一位置**的计数器（`MotionController` 内）；
- 阈值用**具名常量**声明，使"持续"可数、可注入、可测；
- **主动复位与看门狗复位都会丢 PWM。** 优势**不**来自"主动复位能保住输出"，而来自**复位前那段中立流程**：主动路径有机会先把六路写到中立、再写故障记录、然后才复位；看门狗路径没有这个机会。因此本节阶梯的价值在于**抢在复位之前完成中立化**，不能表述为"主动复位更安全"。

### 8.5 故障出口（`Error_Handler`）

现状 `Error_Handler()` 是 `__disable_irq(); for (;;) {}`，被 `configASSERT`（`FreeRTOSConfig.h:41`）、`vApplicationStackOverflowHook`、11 处初始化检查调用。

**只去掉 `__disable_irq()` 是不够的**，会同时留下两个漏洞：

| 情形 | 只去掉关中断后的后果 |
|---|---|
| IWDG **尚未启动**（启动早期故障） | 永久死循环，**没有任何东西会复位它** |
| IWDG **已启动**且中断仍开启 | 其他任务继续被调度 → 可能**继续输出**，甚至**继续喂狗** → 故障被完全掩盖 |

因此故障出口需要三件事：

**1) 统一故障锁（fault latch）** —— 先置位，再做事。

```c
// 所有输出路径在写入执行器前必须检查
std::atomic_bool gFaultLatched{false};   // 一旦置位，永不自动清除（仅复位清除）
```

- 致命故障置锁后禁止普通输出和喂狗；唯一专用无锁出口仍允许写中立。输出故障的受控中立阶段另有40ms期限，正常推进该阶段时继续喂狗，结束才复位。
- 各任务主循环应在检查点发现锁定后**停止本周期工作**，而不是继续跑；
- 这解决了"其他任务继续输出/喂狗"的漏洞，比关中断更精确（关中断会连带破坏 IWDG 之外的其他时序）。

**2) 最小记录（不依赖 RTOS 锁、不等通信）**

- 写入 `.noinit`：故障类型、PC、LR、tick；
- `.noinit`使用魔术字、版本、CRC及提交标记；与RCC复位标志共同判断，掉电不承诺保留。
- 顺序固定：先锁定普通输出，再专用无锁中立，再写无锁记录；不能为记录留下旧目标继续输出的窗口。

**3) 分两种情形处理复位**

| 情形 | 动作 |
|---|---|
| IWDG **已启动** | 置锁 → 尽力写中立 → 写记录 → **停止喂狗，等 IWDG 复位** |
| IWDG **尚未启动** | 置锁 → 尽力写中立 → 写记录 → **主动 `NVIC_SystemReset()`**（否则永久挂死） |

- 两种情形都必须**先尽力写中立**：虽然复位本身会丢 PWM，但"先中立再复位"与"带着旧值复位"在电调侧的行为可能不同（§14 第 1 项），这是唯一能争取的部分。
- 故障类型至少区分：断言 / 栈溢出 / 硬件异常 / 初始化失败 / 输出失败超限。
- 复位原因已进入MotionDiagnostics及固定保留RAM，可通过GDB读取；网页显示需二期两端字段解析更新。保持128字节帧长不等于无需协议语义扩展。
- HardFault、断言、栈溢出与初始化失败走此出口：**尽力中立、不依赖 RTOS 锁、不等待通信**，留下固定记录后等待复位。

### 8.6 启动流程的喂狗所有权

- 启动流程向运动任务**单向交接**喂狗所有权；**2000 ms 电调初始化等待纳入预算**（切分喂狗，见 §8.2）。
- 烧录维护阶段另有明确的全停锁与看门狗处理（§10），**不能直接停核后任由 IWDG 打断擦写**。

## 9. 向量表与写入白名单

- 链接脚本、Bootloader、打包器、S3 升级器与 OpenOCD 脚本使用**同一套固定布局定义**，不能各自维护不同地址。应用 `SystemInit` 也必须使用对应槽的 VTOR，不能跳转后又改回零偏移。
- **STM32 向量表位于槽起点且按 512 字节对齐**；初始 MSP 按当前 128 KiB SRAM 链接布局检查：8 字节对齐且 `0x20000000 < MSP <= 0x20020000`。
- `Reset_Handler` 须带 **Thumb 位**，清除此位后的入口必须落在本镜像实际写入范围；向量表须完整，非保留处理器/IRQ 入口按本固件链接规则验证，**不能指向另一槽、Bootloader 或外部未知地址**。
- **逐段校验 ELF/HEX 的装载地址**；BIN 必须有已验证的链接基址、长度、目标型号、布局版本和摘要。**拒绝溢出、越界、错槽、截断与伪装文件，不能只检查首地址。**
- 普通应用升级**只能擦写非当前应用槽对应扇区**；**不能整片擦除**，不能触及 Bootloader、当前已确认槽、OTP 或选项字节。**启动记录只允许专用状态提交接口操作，不接受任意上传覆盖。**
- **Bootloader 跳转前清理 SysTick 及中断状态，设置 VTOR/MSP，以受控复位态交接**；不能沿用升级器或旧 RTOS 栈。
- **Bootloader 永不通过 OTA 更新，只走有线维护。** 理由：擦写扇区 0–1 期间断电 = 设备永久变砖，**没有任何软件 A/B 能救**。这不是流程约定，是物理约束。
- **普通应用 OTA 不升级 Bootloader、分区表或设备身份数据**；这些变更单独走有线维护流程。
- **通用 CMSIS-DAP / OpenOCD 具有调试权限**，不能声称普通 OTA 白名单同时约束任意调试命令。正常网页升级走受限接口；**维护调试与升级互斥**，开发脚本也禁止默认整片擦除。可在首次部署验证后对 STM32 Bootloader 扇区配置写保护；本轮**不实际修改**选项字节、RDP 或 S3 eFuse。
- **不提前提升会禁止旧版本启动的不可逆防回滚计数。**

## 10. SWD 擦写时序

**目标状态不是"全程保持复位"，而是"复位已释放、CPU 被调试单元停住、且看门狗被冻结"。** 这是三个不同的状态：

| 状态 | 应用会跑吗 | IWDG 会算吗 |
|---|---|---|
| nRST 拉低 | 否 | 否（随复位一起清） |
| **nRST 释放 + CPU 被调试停住** | 否 | **会**（LSI 独立运行，核心停住时没人喂） |
| nRST 释放 + CPU 运行 | 是 | 会（由应用喂） |

**第二行是危险区**：只把核心停住、不冻结看门狗，IWDG 会在擦写途中超时复位，留下半擦扇区。

正确顺序：

```
1. 确认全停：六通道均为中立值，且已写入成功（writtenMask 覆盖全部）
2. 拉低 nRST（让芯片进入已知复位态，中断应用运行）
3. 通过 SWD 建立连接，并使能复位捕获（reset-catch，按所选探针配置）
4. 释放 nRST，保持"CPU 停住"状态；确认核心确实停在复位向量而非继续运行
5. 冻结 IWDG（F4 为 DBGMCU 的 IWDG 冻结位，DBGMCU_APB1_FZ bit12；POR清除，普通系统复位不清除）
   并读回确认；此后核心停住期间 IWDG 不再计数
6. 按扇区擦写非当前槽 → 校验（S3 侧算 SHA-256 / CRC32）
7. 写启动记录（§3.2 协议）
8. 复位并释放，确认进入目标槽
```

要点：

- 复位下连接可配置调试寄存器，普通Flash编程应在释放复位并确认停核后进行，不能混淆两者。
- **第 5 步是必须项**，不是可选优化。仅靠"提前拉低 nRST"无法保证擦写期间不被 IWDG 打断。
- 无法可靠建立停核与调试冻结状态时拒绝擦写并报告原因，不使用全程拉低nRST作为编程退路。
- **IWDG 一旦启动不能用普通软件停掉。** SWD 维护必须明确处理停核时的调试冻结、编程步骤和恢复/复位，**不能让它无计划复位，也不能在正常运动时用后台喂狗掩盖失效**。
- **具体寄存器位与探针配置必须上板实测**，不能只凭参考手册定稿。
- S3 自身崩溃/重启后，先检查未结束的维护事务，释放或停住 STM32，**回到已确认启动选择**。

## 11. 升级事务

1. **上传与落盘。** 验证包头 / 清单 / 长度 / 目标 → 分块写 S3 临时文件并校验 → 完整落盘、读回摘要一致后才标记可用。断网/超时保留原可用包；**残件不成为可烧录文件**；**续传必须匹配同一包标识、长度与摘要**。
2. **取得全停锁。** 两端升级**串行**，确认鱼已全停且中立写入完成，撤销旧目标并拒绝新运动指令。确认升级目标、当前槽及**真实 Flash 容量**（首次连接读芯片型号，不匹配即拒绝）。**无可靠全停确认时不开始擦写。**
3. **写非当前槽。** S3 自身用 ESP-IDF OTA API；STM32 由 S3 受限 SWD 升级器按 §10 时序、按扇区擦写非当前槽。每步有限超时 / 有限重试；失败能释放资源；**迟到回调不能重启已取消的事务**。
4. **读回验证（S3 侧）。** 比对持久镜像长度、完整 SHA-256、向量/镜像头、版本兼容性。**验证失败不改变当前启动选择。**
5. **提交待试运行。** 只有整镜像通过才写新的启动记录，按 §3.2 写内容 + CRC + 最后写标记位。读回确认后才可用；**提交前旧选择始终有效。**
6. **试运行与确认。** 重启后保持运动禁止。自检需看到**关键任务完成周期**、基本服务可工作、必要内部检查通过。**不能因任务创建成功就确认**；**不能要求用户已连 Wi-Fi / LoRa 在线 / 电池电压正常**才能证明程序自身可运行。自检失败、超时、HardFault、看门狗复位、或未确认掉电 → **回到旧的已确认槽**，并递增试运行已用次数（有上限）。
7. **结束。** 保存升级/回滚结果，释放维护锁。**仍保持停机**；满足启动条件并收到新的有效运动指令才能运行；**不恢复升级前目标**。

补充约束：

- **S3 与 STM32 不同时切换版本。** 每次只确认一端；发布清单约束两端 SPI 协议兼容范围；遇不兼容组合**不放行运动启动**，不自动覆盖另一个已确认版本。
- **首次安装**新 STM32 布局需用受控 USB/SWD 流程安装 Bootloader、启动记录和首个应用；当前从 `0x08000000` 运行的旧 BIN **不能直接当 A/B 应用**。首次布局安装与后续应用 OTA **分开交付**，保留有线恢复入口。

## 12. S3 侧边界

S3 沿用 ESP-IDF 原生 A/B + 双扇区 otadata，`CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE=y`。8 MiB 分区与用途：

| 区域 | 地址 | 容量 / 用途 |
|---|---|---|
| 引导与配置 | `[0x000000, 0x020000)` | 128 KiB，Bootloader / 分区表 / NVS / otadata；**普通 OTA 不替换** |
| `ota_0` | `[0x020000, 0x220000)` | 2 MiB |
| `ota_1` | `[0x220000, 0x420000)` | 2 MiB |
| `vfs` | `[0x420000, 0x607000)` | 1948 KiB，存放 STM32 升级包 / 清单 / 恢复文件 |
| `webpage_vfs` | `[0x607000, 0x620000)` | 100 KiB 只读 |
| `storage` | `[0x620000, 0x800000)` | 1920 KiB，未经评估**不挪用、不格式化** |

- 两个 S3 槽已保存本机新旧程序，**不额外复制两份完整 S3 BIN** 到文件系统。S3 收到的本机升级可先存临时文件；仅在全停后导入非运行 OTA 槽，校验完成才选择它启动。**包较大而文件系统空间不足时拒绝缓存**，保留现有已确认内容，**不自动删掉恢复文件**。
- STM32 发布包包含对应固定地址的 A/B BIN 及签名清单，集中保存在 S3 Flash；**只保留当前候选与必要的已确认恢复版本，不存无穷历史**。ELF、MAP 等调试文件仍在电脑，**PSRAM/RAM 用于分块缓存，不能作为断电恢复副本**。
- `ota_upgrade.c` 已有签名清单、SHA-256、硬件/布局/长度限制，只写非运行槽，并使用 ESP-IDF OTA API。**保留这些实现，不另造 S3 引导器。**
- `amphilink.c` 目前在初始化函数返回后**立即确认**新应用，尚未观察运行健康窗口；**需改为观察健康窗口后再确认**，不能把"创建任务成功"当成"服务已正常工作"。
- **S3 自身重启期间网页显示离线，不能伪造实时进度。**
- **S3 侧需配合 §4.3 的启动宽限。**

## 13. 网页显示

### 13.1 必须显示的内容

- 当前控制来源；
- 运行状态（§5.1 四态）；
- **是否允许启动**，以及**所有当前禁止启动原因**；
- 一般告警；
- 最近停机 / 复位 / 升级结果；
- 数据年龄（电压、链路等）。

**历史原因与当前阻断原因必须分开** —— 恢复后的旧告警**不能永久禁止启动**。

至少覆盖：S3 升级中、STM32 升级中、SPI 断链、两路控制不可用、等待新指令、电池低压/过压/采样无效或过期、升级校验失败/回滚。

### 13.2 告警分级

- **可恢复 UART 错误、偶发 CRC 错误/丢包、非关键设备异常** → 只记告警；
- 它们最终若造成**控制来源有效期结束**，则按链路规则降级，**不另建一套全停条件**；
- **一般告警不因自身停止鱼**（§5.3 规则 9）。

### 13.3 SPI 断链时的显示约束

- 由 **S3 本地超时**显示"STM32 通信中断，实时状态不可用"；
- **不能把缓存的 STM32 原因当成实时信息**；
- S3 自身烧录或重启期间，网页可能暂时不可用；已打开页面显示**设备离线**，重连后刷新结果；
- **无法从一个 SPI 超时推断 STM32 内部具体故障** —— 不得在网页上做这种推断。

### 13.4 升级进度显示

显示**上传 / 验证 / 写入 / 读回验证 / 试运行 / 已确认 / 已回滚**阶段，当前目标和槽、进度及失败原因。保存最终结果供重连查询。

## 14. 上板必须优先验证（按顺序）

1. **MCU 复位 / 无 PWM 时电调的实际行为。** 影响：上电行为、看门狗复位行为、崩溃行为。当前 `configurePwmChannel` 设 `Pulse = 0`，这**不是电气中立**，而是"无信号"。若电调保持最后有效值，则"复位=安全"的假设不成立。**此项不确认，看门狗策略无法定稿。**
2. F405完整硬件CRC扫描时间实测，使用Bootloader实际HCLK；理论4HCLK/字仅作核算参考。
3. **IWDG 启动预算与初始化后重设超时的安全性**（§8.2）。需实测：初始化期长预算能否覆盖最坏启动路径；重设 `IWDG_PR`/`IWDG_RLR` 期间是否会提前超时；电调 2 秒等待切分为可喂狗片段后的实际喂狗节奏。
4. SWD复位捕获、停核和DBGMCU冻结读回必须实测；无法验证则拒绝擦写。
5. SPI 8 MHz / 1 ms / 100 µs CS 间隔的实际裕量。
6. ADC 精度与万用表对照。
7. 任务 WCET 与栈高水位（同时用于确定各任务期限常量）。
8. 电调解锁 2000 ms 的实际行为。

## 15. 验收条件

### 15.1 升级可靠性

在下列位置反复**断网、复位、切断电源**：上传中、任一扇区擦写中、最后一块写入时、读回验证时、启动记录切换/回收时、首次启动及确认时。另注入：**坏包、错误地址/向量、错芯片、错槽、重复提交、存储不足、新应用卡死**。

合格条件：

- **不进入半写镜像**；
- **至少一份已确认应用与有效启动选择保留**；
- 未确认新程序失败**能回退**；
- **复位不自启运动**；
- **Bootloader / 分区表哈希不变**；
- **网页重连能读到真实结果**；
- **USB/SWD 任意整片覆盖与硬件损坏不伪装成受保护 OTA。**

### 15.2 安全降级（一期可全部主机验证）

- 启动阻断**不影响已运行的健康 LoRa**；
- 链路失效 → `SURFACE`，且**舵机保持冻结角度、双桨立即中立**；
- 主动全停与复位后**不自启**；
- **普通告警不停止鱼**；
- **电池异常仍停机**，覆盖人工控制与上浮；
- **旧目标不复活**（代次推进有效）；
- **`SURFACE` / `WAIT_COMMAND` / `BATTERY_STOP` 期间持续喂狗**（不会被自己的看门狗打断）；
- **关键任务卡死 → 进度停止 → 看门狗复位**；
- **输出持续失败 → 有限重试 → 尽力中立 → 受控复位**，且全程喂狗；
- 故障出口写入固定.noinit记录，内部诊断可读；网页解析属于二期。

测试接入：一期状态机实现为 `src/algorithm/` 纯函数后，复用现有 `tests/` 主机回归框架（`run_host_tests.py` 的 7 组 + `control_stubs` 可编真实 `MotionController`）验证，**零硬件成本**。

## 本轮固定二进制契约与证据

启动记录v1为120字节，日志槽步长128字节，两个16KiB物理扇区分别容纳128槽。头部8个32位字段依次为magic、format、sequence、confirmed、candidate、state、attempts、confirmed_mask；随后两份40字节镜像描述（size、原生CRC、32字节SHA-256），末尾为记录CRC和最后提交字0xA55AA55A。CRC覆盖前112字节，提交字不参与CRC。待试运行候选的confirmed_mask位必须为0，确认成功才置位；旧槽描述保留用于独立回滚。

Fault RAM固定64字节：magic、version、reason、PC、LR、detail、RCC复位标志、sequence、tick、5个保留字、CRC、最后提交字。正常复位读取并消费，POR/BOR丢弃。真实故障可能破坏栈或RAM，记录为尽力诊断，不能代替RCC复位标志。

原生CRC使用固定0x04C11DB7多项式、0xFFFFFFFF初值、不反射、不做末尾异或；文件按小端32位组字、每字高位先算，不足4字节补FF。不能与RFS1数据帧CRC或默认zlib算法互换。实际Debug/Release工厂镜像均经生产BootStore的主机后端重新解码及校验两槽CRC。

证据入口：build/safety-regression.log；stm32f405/build/debug和release下Testing/Temporary/LastTest.log；固件清单stm32_ab_manifest.json与根validation.json。二期受限无线升级、S3延后健康确认、网页原因字段、新会话握手及上板验证仍未完成。
