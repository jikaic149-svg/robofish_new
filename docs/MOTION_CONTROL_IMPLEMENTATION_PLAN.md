# 运动控制分层实施计划

状态：2026-10-15 用户改为授权一次完成所有层代码。L0–L3 开环链路、树状 L2、传感器接入契约和四轴算法入口已实现；实际变更、测试、论文核查与待测边界见[运动控制验收](../.agent_reports/motion_control_acceptance_2026-10-15.md)。阶段 6 的实物标定及阶段 7 的新闭环尚未完成，不能以软件测试替代。

下文保留实施前的阶段安排和比较算例；其中旧 `mode/FusedMotion`、SDK 双配方等只作为迁移基线，已由 `control/l0`、`control/l1`、`control/l2/{Allocator,tail,propulsion,pectoral}` 与现有 Device 执行层替代。当前源码入口以验收文档为准，旧标定数值不再是另一套运行配方。

设计依据：[运动机构与控制设计](MOTION_LAYERING_DESIGN.md)、[胸鳍与浮沉研究](../pectoral_fin_depth_control_report.md)。现有停止、租约、故障与恢复行为以[安全与升级设计](SAFETY_AND_UPDATE_DESIGN.md)为基线。

## 1. 第一版交付目标

第一版形成一条可回放、可诊断、可标定的开环运动控制链：

```text
已有控制来源
  → L0：来源适配、控制权与模式意图
  → L1：统一的机体请求
  → L2：四舵机 / 双桨目标与限制原因
  → L3：标定映射、电压补偿、PWM 与逐通道提交结果
```

Hybrid 作为主要联合验收工况，尾部和双桨共同参与推进；Prop、Bionic 保留为已有模式和单机构对照。全程混合可以是基线方案，各机构参与程度需要标定，不预设低速 / 高速强制切换点。

第一版验收的是命令语义、输出轨迹、约束和可重复的开环运动。新的姿态 / 深度 / 速度闭环，以及时间不对称尾摆、间歇摆动等高级方案，在基本链路和测量条件成立后分别推进。已有视觉 / PID 策略通过适配保留，其既有作用与新增闭环分开验收。

## 2. 推进顺序

接口先定义，实现从执行端向上推进。这样每完成一层，上层就有可验证的输出边界；L2 工作较多，拆成单机构和混合分配。

| 阶段 | 工作范围 | 阶段产物 | 进入下一阶段的条件 |
|---|---|---|---|
| 0 | 现状基线与接口契约 | 现有回归结果、逐周期基准、字段 / 所有权约定、行为变更清单 | 能稳定重放当前行为，待修改行为已单列 |
| 1 | L3 执行层 | 明确的标定 / 补偿 / 写入边界和提交结果 | 给定目标得到确定输出，部分失败不污染状态 |
| 2 | L2 单机构 | 双桨、尾部、胸鳍三个可独立检查的计算单元 | 各自的轨迹、范围、反向语义与限速通过检查 |
| 3 | L2 混合与过渡 | Hybrid 联合目标、共享约束、模式过渡 | 组合输入可行，限制原因可解释，过渡有连续性证据 |
| 4 | L1 统一指令 | 四轴请求的语义、合法性和停止契约 | 同一机体请求经同一分配入口执行，单位 / 符号一致 |
| 5 | L0 来源与策略 | LoRa 适配及后续本地 / 视觉适配 | 来源切换、旧目标失效、授权和租约符合现有约定 |
| 6 | 台架与整机标定 | 本机几何、轨迹、推力和混合输入数据 | 能给出注明工况的实际运动能力与默认参数 |
| 7 | 后续闭环与高级方案 | 每次一个具体被控量或运动方案 | 具备所需观测、执行权限和独立验收结果 |

阶段 6 是集中完成本机标定与整机验收；零位、安装方向等事实应在阶段 1 / 2 的台架条件允许时提前确认。缺少硬件测量时可以完成软件契约与回放，但不能把软件通过写成实机通过。

## 3. 阶段 0：建立可比较的起点

### 3.1 核对并运行现有检查

现有工程根目录 [tests/run_host_tests.py](../tests/run_host_tests.py) 编译真实 MotionController 和运动计算，提供九组主机回归及网页检查。重点复用电压前馈、实际控制器停机 / 恢复、控制代次和部分提交覆盖，不另建平行测试框架。

STM32 使用 [CMakePresets.json](../stm32f405/CMakePresets.json) 中的 debug / release 配置；现有 CTest 检查 A/B 应用和 Bootloader 的 ELF 约束。阶段 0 才实际运行并记录结果，本次计划编写不认领此前结果为新基线。

### 3.2 录制逐周期基准

先在主机模拟时间与驱动提交，固定源码文件哈希、工具链及输入序列。记录：

- 输入来源、模式、目标、序号 / 代次与模拟时间。
- 相位、六路名义目标、共同 / 差动推进量、限制原因。
- 电压补偿结果、逐通道写入掩码和最后成功提交的名义值。
- 停止、模式切换、短周期、延迟周期、时间回绕和写入失败时的结果。

代表性序列覆盖前进、左右转、前进叠加转向、俯仰、旋钮、各模式切换、停止、负推进请求和安全退出。

结构调整以基准输出为比较对象；“尾摆取反即后退”等已知错误只记录为旧行为，不被当成必须保留的正确性标准。修复这些行为时，单列预期差异和新验收条件。

### 3.3 先定义接口，暂不切换生产链路

建议第一版统一请求使用四轴百分比和使能：

| 字段 | 语义建议 | 单位 / 正向 |
|---|---|---|
| surge | 归一化推进请求 | −100～100，前进为正；不是测得航速或速度闭环设定值 |
| yaw | 归一化偏航请求 | −100～100，右转为正；不是角速率 |
| pitch | 归一化俯仰请求 | −100～100，抬头为正；不是直接垂向推力或深度 |
| roll | 归一化横滚请求 | −100～100，正向需在本阶段统一；实机输出默认保持零直到映射确认 |
| enabled | 本周期是否有正常运动请求 | 不替代全部安全状态和停止事件 |

模式由 L0 选择并作为分配上下文传给 L2；来源、序号、时间戳、控制代次和权限快照属于请求上下文。L1 四轴字段不包含舵机、脉宽或安装反向开关。

L2 输出继续表达四路目标角和两路名义推进百分比，明确每个角是何种标定坐标；百分比不标为牛顿。逐通道成功提交的名义值、电压补偿后的电气命令和实际测量值分别记录。

水平停止、全停、租约退出及电池停机沿用各自的目标清理与输出语义，不能简化为同一个 enabled=false 后全部回中。

**本阶段验收**：基准可重复；四轴与六路单位、符号、所有权和停止语义有书面表；后续行为变化能从基准中明确识别。

## 4. 阶段 1：L3 执行层

### 工作

- 从现有 [RoboFishDriver.cpp](../stm32f405/src/device/motion/RoboFishDriver.cpp)、[EscCalibration.h](../stm32f405/src/device/motion/EscCalibration.h) 和六路 Device 继续整理。
- 明确几何目标到舵机命令 / PWM 的映射，将安装方向和电气补偿收在一个清楚的边界；迁移时逐项核对现有上游符号，避免重复反向。

- 复用 `FrameApplyResult`、`writtenMask`，使部分写入失败的结果与每个通道对应。
- 把最后成功提交的名义状态更新集中到一个明确位置；驱动成功不解释成真实位置到达。

当前尾中立 90° / 86°等双配方差异先作为兼容问题列出。职责迁移不擅自选定真实机械中立；暂存的旧配方差异须有明确归属，后续依据台架数据逐项合并。

### 验收

中立、端点、正负推进、无效输入、电压变化与饱和、单路失败、双桨部分失败均得到确定结果；现有安全输出与前馈回归通过。结构调整部分与逐周期基准一致。

独立电气速率兜底属于另一个行为设计，须先明确阈值与停止路径关系，不随本阶段职责整理附带加入。

## 5. 阶段 2：L2 单机构，每次完成一个

L2 的工作是把一个周期的机体需求变成**六路能执行的名义目标**。它既包含几何分配，也包含时间上的轨迹约束。先拆清计算和状态，再改变运动行为。

### 5.1 输入、输出及计算边界

| 输入 | 具体内容 | 用途 |
|---|---|---|
| 机体请求 | surge、yaw、pitch、roll、enabled | 表达本周期需要的推进、转向与姿态作用 |
| 模式 | Idle / Prop / Bionic / Hybrid | 决定哪些运动方案参与 |
| 已选配方 | 幅值、频率、相位差、偏置增益、推进权重、限速参数 | 是参数，不由分配函数再次按来源选择 |
| 几何标定 | 中立参考、各侧上下限、端点映射 | 将请求转换为目标角，并求剩余行程 |
| 时间 | 当前时刻、实际经过时间 | 推进相位，并按既有规则形成限速时间差 |
| 成功提交历史 | 上周期各通道成功提交的名义目标 | 作为轨迹限速起点 |
| 已有动作许可 | 本周期是否运行、是否允许既有造流辅助 | 阻止停止或不支持请求通过辅助策略重新产生推进 |

L2 输出复用 / 收紧 `CoordinatedResult`：四路角度、两路名义桨命令、公共相位、共同 / 差动量以及限制原因。新增诊断只选择定位问题所需的小量字段，例如请求 / 有效幅值和模式不支持原因。

L2 不把百分比解释成牛顿，不测电压，不写 PWM，不修改控制权，不判断 LoRa 是否在线，也不把内部预测角当成传感器反馈。

旧 SDK 的独立尾 / 桨请求和档位行为先在兼容适配边界显式保留，使用同一批计算单元；它们合并后的行为必须有对照记录。公共四轴接口不能靠丢弃这些旧字段来获得表面上的统一。

### 5.2 一个周期的处理顺序

| 顺序 | 处理 | 产物与检查 |
|---|---|---|
| 1 | 控制任务取得同一周期的请求、模式、权限和提交历史快照 | 计算期间不混入另一个来源的半份目标 |
| 2 | 处理停止和模式能力 | 纯尾负推进不会继续进入反相波形计算；停止路径撤除造流许可 |
| 3 | 读取配方并处理已允许的推进辅助 | 得到本周期的有效推进请求；记录它与原请求的差异 |
| 4 | 计算各机构基础目标 | 桨共同 / 差动请求，尾部偏置与请求幅值，胸鳍基础角与修正量 |
| 5 | 处理共享约束 | 桨分配余量、尾部偏置 / 摆幅余量、两胸鳍共享行程 |
| 6 | 公共相位推进一次，生成两关节周期目标 | 前后关节共用同一相位，不分别读时间生成波形 |
| 7 | 从成功提交历史向候选目标做轨迹限制 | 四鳍角速度与桨过渡规则分别生效，保留第一版各路径差异 |
| 8 | 最终范围 / 有限值检查，形成唯一六路帧 | 输出名义坐标与限制原因，不做电压补偿 |
| 9 | 控制任务在提交前应用现有停止 / 故障检查，交给 L3 | 新来的停止事件仍遵循现有优先级和停止代次契约 |
| 10 | 控制任务按提交掩码更新历史并记录诊断 | 下一周期只从各通道成功提交的名义值继续 |

上述是目标职责顺序。兼容重构先保持现有取整、裁剪和渐变次序；若改动次序使输出变化，单列为策略变化，不能混入等价迁移。

#### 5.2.1 配方怎样从请求中计算出来

内部字段仍使用百分比；计算时可令 `s=surge/100`、`y=yaw/100`、`p=pitch/100`、`r_cmd=roll/100`。这些量表示请求强度，不能直接代入牛顿 / 牛米公式。

第一版以当前配方做确定性基线，调度顺序如下：

| 计算项 | 第一版做法 | 后续可能调整的内容 |
|---|---|---|
| 尾推进幅值 | `A_requested = A_max × drive × driveScale × tailWeight`；drive 为有效正推进量，Bionic 零推进转向保留以 yaw 驱动的旧语义 | 实测后再定义非线性幅值调度 |
| 尾频率 | 从模式配方取得固定值 | 需要变频时，联合幅值与带载速度限制设计 |
| 关节相位差 | 从模式配方取得固定值 | 不在本阶段加入动态最优相位 |
| 尾平均偏置 | `bias_i = yaw × turnGain_i`，增益带几何方向与度 / % 单位 | 分关节权重、时间不对称转向另做比较 |
| 桨共同请求 | 有效 surge 经过模式推进权重 | 功耗分配权重以实测为依据 |
| 桨差动请求 | yaw 经过模式差动增益 | 饱和时按明确优先级裁剪 |
| 胸鳍基础目标 | pitch 经过各侧的分段端点映射 | 真实角度 / 作用标定后替换参数 |
| 胸鳍差动修正 | roll 经过确认后的左右几何映射 | 与基础目标共享行程；实物 roll 开放单列 |

配方包括幅值、频率、相位差、增益与限制；它不包含 LoRa 包解析、PWM 脉宽或电压补偿。尾 / 桨权重作用于命令配方，不称为已知的物理推力占比。

既有造流辅助需要特别处理：当前代码可以在明确许可下，因俯仰请求提高有效 surge。它会影响尾部幅值和 / 或桨共同量，所以必须在这张表之前完成并记录。新的纯 pitch 请求默认不能凭空理解为已经请求某个前进速度；兼容升降动作的许可在来源 / 动作契约中明确传递。

#### 5.2.2 每周期伪代码

下列名称说明职责，最终实现优先复用现有类型和函数；这不是已经提交的固件接口。

```text
stepL2(request, mode, recipe, geometry, now, elapsed, phaseState, committed):
    1. 根据 mode 和请求判定参与机构 / 不支持的运动
       若普通停止或不支持：产生约定的停止目标，撤除造流许可
       直接进入相应轨迹 / 结果路径，不再用原请求重新生成推进目标
       现有安全强制输出由控制任务处理，不经过这里的普通限速路径

    2. 仅在明确允许时应用已有造流辅助
       effectiveSurge = 请求推进与辅助推进的合成结果

    3. 从 recipe 计算本周期参数
       尾：A_requested、frequency、lag、bias1、bias2、rearRatio
       桨：commonRequested、differentialRequested
       胸鳍：baseLeft、baseRight、rollDeltaLeft、rollDeltaRight

    4. 解共享约束
       桨：得到 commonEffective、differentialEffective
       尾：得到可用幅值与 A_effective
       胸鳍：得到两侧共同允许的修正比例 lambda

    5. 按本周期频率推进公共相位一次
       phase = advanceGait(phaseState, now, frequency)

    6. 生成六路本周期几何 / 名义目标
       tail1 = center1 + bias1 + A_effective * sin(phase)
       tail2 = center2 + bias2 + rearRatio * A_effective * sin(phase-lag)
       finLeft  = baseLeft  + lambda * rollDeltaLeft
       finRight = baseRight + lambda * rollDeltaRight
       propLeft  = commonEffective + differentialEffective
       propRight = commonEffective - differentialEffective
       无周期摆动的模式使用其已定义静态 / 停止目标

    7. 使用各通道 committed 值作为限速起点
       对四鳍应用角速度限制
       对双桨应用本配方已定义的过渡 / 过中立规则

    8. 检查最终目标范围和有限性，返回候选帧、相位与限制原因
       不覆盖 committed，不写硬件，不做电压补偿
```

轨迹推进后，控制任务提交给 L3，并将成功写入的通道更新到 committed。单路失败不会使其他成功通道回到旧值，也不会使相位时间倒退。

#### 5.2.3 一次具体计算

以下用统一几何坐标演示数值流，不是旧固件电气编码的兼容向量，也不代表实物转向标定。设：

| 项 | 示例值 |
|---|---|
| 模式与请求 | Hybrid；surge=60，yaw=20，pitch=20，roll=0 |
| 档位 / 权重 | 本例均取 1，造流辅助关闭 |
| 尾配方 | 最大半幅 25°，后 / 前幅值比 0.9，相位差 72° |
| 本周期相位 | 90° |
| 本例尾转向映射 | 两关节平均偏置均为 +3.6°；仅作给定映射的算例 |
| 本例胸鳍映射 | pitch=20 得到两鳍物理同向偏转 +8.4° |
| 上次成功目标 | 四鳍相对中立偏量为 0，两桨名义请求为 0 |
| 本周期限速 | 四鳍最多变化 5°，两桨最多变化 10 个百分点 |

先生成目标：

```text
A_requested = 25° × 0.60 = 15°
尾1偏量 = 3.6° + 15° × sin90° = 18.6°
尾2偏量 = 3.6° + 13.5° × sin18° ≈ 7.772°
两胸鳍偏量 = +8.4°、+8.4°
桨共同量 = 60，差动量 = 20
两桨目标 = 80、40
```

假设几何行程都允许这些目标，再按上次成功值限速：

| 通道 | 限速前目标 | 本周期可提交的名义目标 |
|---|---:|---:|
| 尾1 | +18.6° | +5° |
| 尾2 | 约 +7.772° | +5° |
| 左胸鳍 | +8.4° | +5° |
| 右胸鳍 | +8.4° | +5° |
| 左桨 | 80 | 10 |
| 右桨 | 40 | 10 |

这个例子显示：求出终点不等于本周期立即到达终点。逐桨独立限速还会在起步时暂时改变共同 / 差动比例；本周期 10 / 10 的差动为零，即使最终目标是 80 / 40。

若希望过渡期间也优先保留差动，需要单独设计联合过渡，例如同时约束共同量和差动量，或对两路增量统一缩放。它不能由静态分配公式自动保证，属于阶段 3 的明确策略选择。

若本周期右桨写入失败，下一周期左桨从成功提交的 10 开始，右桨仍从先前成功的 0 开始。与此同时，尾部相位继续按时间推进；不会因为右桨失败而重放同一拍尾部运动。


### 5.3 时间和状态怎样处理

当前公共相位使用真实时间间隔推进；轨迹限制使用的时间差被 `kMaximumSlewElapsedMs` 限制。它们不是同一个量。例如实际间隔 40 ms 时，相位可能按 40 ms 前进，轨迹限速仍按目前允许的最多 20 ms 计算。第一版保留这一行为并测试，后续再决定是否调整丢周期策略。

状态分为三类：

| 状态 | 谁更新 | 提交失败时怎样处理 |
|---|---|---|
| 公共相位与时间戳 | 运动输出任务调用 `advanceGait` | 单路输出失败不回滚时间；后续安全退出按原规则处理 |
| 本周期候选目标 | L2 本次计算 | 只作为尝试值，不能提前覆盖成功历史 |
| 各通道成功名义值 | 控制任务收到 L3 结果后 | 成功的更新，失败的保留；补偿后的电气值不写入这里 |

当前 SDK 还使用虚拟 throttle / steering 进度，一侧桨失败时存在成对回退。过渡阶段必须覆盖并保留；删除虚拟角表示时，再用新的名义状态验证等效行为，不能直接删掉回退代码。

相位在首次调用、停摆、模式切换与全停后的处理先以当前回放为准。阶段 2 复用积分器；若要改成固定起始相位、Prop 时冻结相位等新规则，另列差异，不把“相位连续”当成可以改变全部初始化行为的理由。

### 5.4 2A：双桨分配的实施任务

**入口与归属**：由 `FusedMotion` 调用双桨计算；输入是统一方向的推进 / 偏航请求和配方参数。安装电气反号交给唯一执行映射。下面的数值是名义命令，均未代表真实推力。

第一步抽出共同 / 差动计算，复现当前共同推进优先规则：

```text
c = clamp(共同推进请求, −100, 100)
可用差动 = 100 − abs(c)
d = clamp(差动请求, −可用差动, +可用差动)
左桨名义目标 = c + d
右桨名义目标 = c − d
```

当前旧路径还在这些结果后乘档位系数。抽出计算时必须保留；是否将档位提前作用于请求，列入阶段 3 的单独策略变更。

| 共同请求 c | 差动请求 | 当前共同优先结果（档位系数 1） | 预期诊断 |
|---|---|---|---|
| 60 | 20 | 左 80，右 40 | 无桨范围限制 |
| 80 | 40 | 差动压到 20，左 100，右 60 | `PropulsionLimited` |
| 100 | 40 | 差动压到 0，左 100，右 100 | `PropulsionLimited`，不能伪报已提供请求差动 |
| 0 | 40 | 左 40，右 −40 | 命令范围可行；不据此承诺物理零平移 |
| −60 | 20 | 左 −40，右 −80 | 两桨均反向，实际转向作用需标定 |

第二步整理过渡。当前 LoRa 路径以 200 ms 变化 100 个百分点计算步长，20 ms 时步长为 10；仅按此规则，+100 到 −100 需要约 400 ms。SDK 使用虚拟角步长，Hybrid 才具有相应的慢加速 / 过中立分支。不能把所有路径描述成已经具有相同中立停留过程，也不在迁移中临时添加等待时长。

第三步把原始请求、有效共同量、有效差动量及限制原因接入已有诊断。

**2A 验收**：上述代数算例、正负方向对称案例、各档位、阶跃、正反向切换和单桨失败后恢复通过；旧路径的取整与过渡结果可重复。

**2A 文件范围**：`mode/FusedMotion.*`、`mode/ActuatorTransition.*`、`config/ControlConfig.h`；涉及 SDK 转换时核对 `ActuatorMapping.*`。优先在现有模块内提取清楚的计算函数，需要独立编译测试时再拆文件。

### 5.5 2B：尾部轨迹的实施任务

**先把参数集中到一个可查表的配方**：前关节半幅、后 / 前幅值比、频率、关节相位差、两关节偏置增益、角速度限制。使用当前配置作为回放起点，参数本身不因函数移动而改变。

纯几何示意为：

```text
前关节目标 = 中立₁ + 偏置₁ + A_eff × sinφ
后关节目标 = 中立₂ + 偏置₂ + r × A_eff × sin(φ − δ)
```

其中 r 是幅值比，δ 是关节相位差；所有符号必须对应阶段 0 的坐标表。旧命令角与新几何坐标的转换在一处兼容边界处理，不让两个公式各自再翻一次安装方向。

**幅值先由请求得到，再用偏置后的剩余行程约束。** 若每个关节的基准角 `b_i = 中立_i + 偏置_i` 已经可行，则：

```text
单关节可用半幅 h_i = min(上限_i − b_i, b_i − 下限_i)
公共幅值上限 = min(h_1, h_2 / abs(r))       （r=0 时忽略第二项）
A_eff = min(A_requested, 公共幅值上限)
```

基准角本身越界时先处理偏置，不把负余量送入正弦。当前实现使用更保守的共同余量；提取阶段先保留其结果，上式推广到不同关节行程 / 比例时按行为变化比对。

**再处理速度需求。** 恒幅恒频正弦的峰值角速度为 `2πfA`；动态偏置、幅值、相位差还会增加变化率。第一版使用已有固定频率 / 相位差，不在本阶段顺手改成频率调速。

当前 LoRa 25°、1.5 Hz 的需求约 236°/s，对应 250°/s 限制；SDK 满请求的 50°、1.7 Hz 与 58°、2 Hz 分别约需 534°/s、729°/s。验收既检查理想目标，也检查限速后的名义轨迹，不把受限波形误报为完整正弦。

**模式与动作表（首版建议）**：

| 模式 / 请求 | 尾部目标 | 桨的关系 / 结果 |
|---|---|---|
| Bionic 正推进 | 带现有相位差的周期摆动，允许叠加偏置 | 桨关闭 |
| Bionic 零推进但有 yaw | 保留当前以 yaw 驱动尾摆的语义 | 不因 surge=0 就删除这一既有转向动作 |
| Prop 正推进或转向 | 保留已定义的静态尾舵目标 | 推进与主要差动由双桨执行 |
| Hybrid 正推进 | 连续尾摆及偏置 | 双桨共同参与 |
| Hybrid 零推进、存在 yaw | 先保留既有零推进配方与尾偏置行为，不凭空增加尾摆 | 当前双桨差动可参与 |
| Prop / Hybrid 负推进 | 首版建议尾部按正常限速到配置中立，停止周期摆动和未标定的反向静态舵分配 | 后退与后退转向由双桨承担，属于明确行为变化 |
| 安全上浮 / 电池停机 / 全停 | 采用现有控制编排给出的相应输出路径 | 不由普通尾部配方覆盖安全冻结或中立动作 |

不支持请求的处理需要控制任务消费 L2 结果并撤除对应旧目标。新拒绝原因先进入现有结果 / 诊断机制；接收 ACK 与执行结果的语义在来源适配阶段核对，不擅改空口协议。

**实施顺序**：

1. 从 `FusedMotion` 和 SDK `ActuatorMapping` 列出两条现有波形路径及调用者。
2. 共用相位输入、几何约束和轨迹函数，保留正常前进的旧参数及取整。
3. 用回放证明普通动作等价，再单独移除“负请求使两正弦同时取反”的分支。
4. 验证不支持负请求不会通过残留 yaw 或造流许可重新启动尾部。
5. 删除已无调用者的旧生成路径；存在调用者的公开辅助函数先改为明确的兼容包装。

**2B 验收场景**：幅值 0 / 中间值 / 满值，左右偏置，两个模式相位差，方向配置，固定时间戳与回绕，模式切换，部分尾通道写入失败，前进到负请求以及带俯仰 / yaw 的负请求。停止后观察至少多个原尾摆周期，确认不会继续周期推进。

**2B 文件范围**：`FusedMotion.*`、`ActuatorMapping.*`、`MotionMode.*`、`algorithm/GaitPhase.h`、现有配置和控制任务结果处理。公共相位积分器已有，不新写另一套。

### 5.6 2C：胸鳍分配的实施任务

先保留当前俯仰端点插值和取整：左中立 90°、端点 132 / 56°；右中立 90°、端点 48 / 124°。这些是现有命令坐标，不声明为实际迎角。

新增共同 / 差动表达时，在统一物理方向的角坐标中计算，再由执行映射处理镜像。几何对称的理想表达可写为 `α_L = α_c + α_d`、`α_R = α_c − α_d`；真实左右标定不对称时分别使用各侧映射。

**首版建议俯仰基础目标优先，roll 修正使用剩余行程**，与已有 `pairedOffsetScale(base, delta, limits)` 的语义一致：

```text
base_L / base_R = 由 pitch 得到的左右基础目标
delta_L / delta_R = 由 roll 得到的左右修正量
λ = 能同时满足两侧范围的最大值，0 ≤ λ ≤ 1
输出_L = base_L + λ × delta_L
输出_R = base_R + λ × delta_R
```

假设两侧范围均为 ±20°、基础目标都是 +15°，roll 请求修正为左 +10°、右 −10°，则 λ=0.5，输出为 +20°、+10°。这是几何算例，不是本机角限。相比独立裁剪，两侧修正保持相同比例，俯仰基础目标的优先级清楚。

实际 roll 增益、正方向与有效水动力尚未标定时，新公共入口默认不激活实机 roll；主机通过假设标定表验证数学路径。现有 yaw / surge / tail 六项胸鳍耦合增益继续按当前零值处理，不补猜测增益。

**实施顺序**：提取当前 pitch 映射 → 核对左右镜像与范围 → 复用成对限制处理组合修正 → 统一胸鳍轨迹限速 → 接入限制诊断。roll 对外开放单独验收。

**2C 验收场景**：pitch 正负端点和零值，roll 为零时与旧输出一致；正负 roll 数学组合、左右不同限位、基础目标近边界、修正为零、连续目标变化及单鳍失败。不得以舵机命令范围代替已验证迎角范围。

### 5.7 L2 检查分成三种证据

| 检查 | 覆盖 | 不能据此声明的结果 |
|---|---|---|
| 几何与代数 | 共同 / 差动公式，组合行程，模式能力，有限值 | 真实推力、滚角或航速 |
| 时间序列 | 多周期波形、限速、切换、停止、失败恢复 | 实物舵机已经跟随 |
| 台架 / 水池 | 实际轨迹、力或运动响应 | 超出所测构型与工况的通用性能 |

组合检查建议使用各轴 −100 / −50 / 0 / 50 / 100 的网格，分模式验证不变量；当前不开放的 roll 先在人工给定标定下做数学检查。时间检查使用代表性序列，不将全部网格无限组合成长时间仿真。

## 6. 阶段 3：L2 混合、约束与过渡

本阶段把已验收的单机构计算汇入唯一六路帧。第一步复现现有联合行为，随后每次只改变一个分配策略。

### 6.1 联合计算的任务包

| 任务 | 改动内容 | 验收点 |
|---|---|---|
| 3.1 | 明确模式配方：哪些运动方案参与，参数从哪里来 | Bionic 的桨为零、Prop 的尾部静态、Hybrid 的组合目标与已定义能力一致 |
| 3.2 | 将单机构目标在同一周期、同一相位上下文内合成 | 不出现不同来源或不同周期的通道拼接 |
| 3.3 | 整理造流辅助及有效请求记录 | 仅在既有明确许可下生效；水平停止、负请求不支持及安全退出不会重新开推进 |
| 3.4 | 统一组合限位与轨迹执行 | 限幅后仍可行；限速使用上次成功名义值；避免一个通道被重复渐变 |
| 3.5 | 核对模式切换与回中 / 保持目标 | 相位、幅值、偏置、频率和状态初始化的变化都有回放依据 |
| 3.6 | 扩展必要的诊断 | 请求、有效分配和提交差异可解释，限制原因可追溯到具体阶段 |
| 3.7 | 对选定的策略变化单独比较 | 饱和优先级、档位位置、反向语义、标定合并分别验收 |

### 6.2 全程混合的首版含义

在正常正向航行中，Hybrid 持续使用尾部与双桨，首先采用固定的当前模式参数；转向叠加尾偏置及桨差动，俯仰叠加现有胸鳍映射。这里不预设能耗最优，也不根据未测得的 St、J、航速阈值自动关尾或切模式。

尾 / 桨权重是可标定的模式参数。第一版先证明同一目标下的组合输出稳定、可解释，之后才通过同速度试验改权重。停止、后退和安全退出继续采用各自明确的动作语义，不能用“全程混合”覆盖它们。

### 6.3 桨饱和优先级单独选择

共同推进优先按 §5.4 执行。若后续选择差动优先，候选公式是：

```text
d_eff = clamp(d_requested, −100, 100)
c_eff = clamp(c_requested, −(100 − abs(d_eff)), +(100 − abs(d_eff)))
左桨 = c_eff + d_eff
右桨 = c_eff − d_eff
```

例如共同 80、差动 40：共同优先得到左 100 / 右 60；差动优先得到左 100 / 右 20。两者都满足范围，但后者主动降低共同推进。选哪一种是产品行为决策，不是数学错误修复。

档位系数在混合前还是混合后作用，同样单列。当前共同 100、差动 40，先裁差动再乘 0.5 档位，会得到 50 / 50；若改成先降共同量再分配，就可能得到不同差动。不能在合并字段时把这种变化隐藏掉。

### 6.4 模式切换与轨迹连续性

每种切换都分别检查：旧相位、旧成功输出、新频率、新幅值、新偏置和新限制值。公共相位保持连续，并不保证相位差或偏置突然改变后目标仍连续。

先使用已有过渡和限速实现目标接续。若提出更平滑的幅值 / 偏置渐入曲线，需要给出持续时间与响应代价，再按单独行为变更验收。不能为了视觉上平滑而随意增加延迟。

特殊场景包括：满幅摆动切 Prop、静态大偏置切 Hybrid、档位骤变、运行中反向请求、停止期间模式变化、单关节连续写失败后恢复。每种情况都记录下一周期从哪一个成功名义值开始。

### 6.5 诊断与运行资源

宿主回放可记录理想目标、共享约束后目标、轨迹限制后目标和提交结果。固件先复用 `MotionDiagnostics` 的尝试帧 / 成功帧、共同 / 差动量、相位和限制位；只增加定位所必需的字段，不在 MCU 内保存大段历史。

限制原因至少区分已有桨余量不足、尾幅值受限、胸鳍成对受限，并按需要扩展不支持反向和轨迹限速。保留现有位值，新原因另分配位；调用方仍能解释旧诊断。

新增诊断和局部计算的 RAM / 栈开销在 ARM 构建中核对。相位、波形与约束计算保持无 HAL / RTOS 依赖；不为每个机构创建 Task、队列或动态对象。

### 6.6 本阶段完成的证据

- 普通组合动作的等价迁移通过基准对照。
- 每一项刻意改变的行为有独立输入序列、旧结果、新结果和说明。
- 不支持反向、造流、水平停止、全停及安全上浮不会相互覆盖。
- 部分写入成功后，各通道下一周期状态正确；已补偿桨命令不会回灌。
- 可用诊断解释“请求很大但输出较小”的具体原因。
- 实机能力仍由台架 / 水池证明；软件验收只说明计算与时序契约成立。

## 7. 阶段 4：L1 统一机体指令

按阶段 0 的契约实现数值合法性、范围和有效请求处理，使普通动作与连续目标都进入同一机体请求形式。旧字段 `heavePercent` 的实际含义应显式适配为俯仰意图 / 既有造流策略，不能更名后声称有独立升沉控制。

L1 不根据硬件或模式选择舵机配方；某模式能否执行负推进属于 L2 的能力约束。来源授权和控制代次仍由编排与 L0 上下文负责。

**验收**：同一来源语义转换后的机体请求具有一致含义；非法数、边界、失效请求、停止事件不会留下新旧请求混用。roll 未开放的入口明确给零或拒绝，不能静默声称已执行。

## 8. 阶段 5：L0 来源适配与策略

### 5A 现有 LoRa 主控

整理文本动作、旋钮和模式选择到统一意图的适配。来源不选择物理标定，也不推进相位或直接写执行器。保留序号去重、租约、模式辅助命令和停止事件的现有语义。

### 5B 本地、视觉与自动化

在已有方法和策略上做适配，先用主机调用验证完整链路。实际开放入口前，核实人工授权、controlGeneration、过期目标、来源切换和相应超时。当前管理网络入口的开放属于独立集成动作，不能由内部重构隐式开启。

跨模块命令与状态使用明确的消息 / 快照边界；连续目标采用已有最新值语义，保留停止等离散事件的处理优先级。复用现有 channel 和任务，不为四层创建四个任务或通用消息框架。

**验收**：相同机体意图不因来源不同而选择另一套硬件中立；退出后旧视觉 / 自动化结果不能恢复运动；没有第二条可以绕过统一分配与执行入口的输出路径。

| 6C | 尾部幅值 / 频率 / 相位与实际尾尖轨迹、航速、功耗 | 能执行的步态范围及推进数据 |
| 6D | 固定来流下胸鳍共同 / 差动响应、净浮力与配平 | 姿态作用、共享行程及升沉起始条件 |
| 6E | 同速度下纯尾 / 纯桨 / 混合，转向与升沉组合 | 首版默认配方、实际能力与适用工况 |

固定速度比较能耗，固定输入观察响应；一次只改变待识别因素。单机构试验允许其他机构提供固定来流。默认参数从本机结果选择，不直接采用论文的频率、角度或 St 阈值。

每次上板属于明确的实施步骤，使用前一阶段的软件验收产物与可识别的镜像。本计划本身不包含实际烧录或运行设备。

## 10. 阶段 7：后续扩展，一次一个目标

完成上述基本链路后，按已有观测条件选择一个专题：

- 已标定视觉下的航向 / 轨迹闭环移接或改进。
- 接入可靠姿态样本后的俯仰或横滚闭环。
- 有深度观测和竖向控制权限后的深度闭环。
- 有可用速度估计后的推进速度闭环。
- 尾部时间不对称、间歇摆动、相位调度或能耗分配试验。

闭环位于 L0 的意图到机体请求之间，复用 L1～L3。先定义被控量、观测单位 / 坐标 / 延迟、输出权限和失效行为，再实施控制器；不同时引入所有反馈环和所有新步态。

## 11. 贯穿各阶段的检查与决策

### 11.1 现有运行边界

沿用现有控制任务与时间源，控制周期仍为 20 ms；计算单元保持无 HAL / RTOS 依赖，运动状态由输出任务推进。保留静态内存、有限等待、逐通道提交及已有安全 / 故障恢复。四层是职责划分，不对应新增四套运行设施。

### 11.2 需要分阶段决定的五项

| 决策 | 最晚在哪个阶段确定 | 当前建议 / 所需依据 |
|---|---|---|
| 四轴含义、零值与正向 | 0 | 使用归一化推进 / 转向 / 姿态力度请求；显式转换现有 FLU 观测符号 |
| 纯尾负请求、Hybrid 后退时尾部姿态 | 2B | 纯尾不声明后退；Hybrid 由桨反推，尾部经正常限速到中立，按独立行为变化验收 |
| 90° / 86°、安装极性、真实限位 | 1 开始登记，6A 完成实物确认 | 职责迁移先保留兼容输出，物理标定最终唯一，不凭来源选零位 |
| 推进与转向、俯仰与横滚的饱和优先级 | 3 | 先建立原策略基线，再比较改变优先级的收益与代价 |
| 本地 / 视觉开放和 roll 对外接口 | 5 | 授权、代次、租约及方向 / 权限证据完整后单独集成 |

这些问题按所处阶段处理，不要求在写第一层之前一次性猜定所有水动力参数。

### 11.3 每阶段交付格式

1. 本阶段改了哪些职责和文件。
2. 哪些输入 / 输出或实际行为有变化，以及原因。
3. 主机检查、Debug / Release 构建及适用的 CTest 结果。
4. 对照基准的差异、硬件已确认与待确认项。
5. 本阶段完成状态，以及下一阶段所需输入。

相关代码变化后复用现有回归，并补充能发现该层错误的最小检查；不以重复实现一遍算法的测试代替边界和故障验证。每阶段只保留一个清楚的生产输出路径，旧适配完成迁移后移除。
